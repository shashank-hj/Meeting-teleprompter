Local Real-Time Meeting Teleprompter

Status: Proposed architecture
Date: 29 August 2026
Initial platform: Windows 10/11, CPU-only, 16 GB RAM

1. Product idea

Build a Windows desktop application or widget that listens to live Google Meet, Zoom, and Microsoft Teams calls, follows the conversation in real time, retrieves relevant material from user-provided sources, and proactively presents useful information or suggested responses.

The product should behave like an intelligent teleprompter rather than a conventional chatbot. It should keep listening and updating its suggestions without requiring a direct question or prompt. Suggestions may offer user-selectable routes such as generating a concise answer, finding supporting evidence, explaining a concept, checking a claim, searching indexed sources, searching the web, or suggesting a follow-up question.

The application should run its speech recognition, retrieval, embeddings, conversation tracking, and answer generation locally. Network access is limited to fetching user-provided URLs and, if introduced later, explicitly enabled live web search.

2. Goals

  • Capture meeting audio without separate integrations for Meet, Zoom, and Teams.
  • Maintain a continuously updated transcript and compact conversation state.
  • Surface relevant information even when nobody asks a direct question.
  • Ground suggestions in local files and user-provided web pages.
  • Preserve citations and source freshness information.
  • Keep meeting audio, transcripts, embeddings, and model inference on the device.
  • Remain usable on a Windows computer with 16 GB RAM and no dedicated GPU.
  • Keep transcription responsive while lower-priority retrieval and generation work is running.
  • Make models and inference runtimes replaceable as better edge models become available.

3. Non-goals for the first version

  • Separate integrations with each conferencing product.
  • Fully autonomous participation in calls.
  • Reliable identification of every remote speaker.
  • Continuous deep reasoning over every transcript fragment.
  • Automatic refreshing of saved web sources.
  • Cloud-hosted transcription, embeddings, or answer generation.
  • Detailed optimization of the final card layout and interaction design.

4. Confirmed product decisions

Platform and hardware

  • Windows is the initial and only required platform.
  • The baseline machine has 16 GB of system RAM and uses CPU inference.
  • The design must not assume a dedicated GPU, although optional integrated-GPU or NPU acceleration can be added later.

Interaction model

  • The application listens continuously during an active session.
  • It updates suggestions in real time as the discussion changes.
  • It may suggest information when topics, entities, claims, risks, or decisions arise, even without a recognizable direct question.
  • Suggestions can expose multiple clickable routes that let the user choose how to pursue the topic.
  • Detailed behavior for expanding, replacing, or focusing suggestion cards is intentionally deferred.

Sources

  • Users can select one or more local directories.
  • Users can provide web links.
  • A web link is fetched and indexed immediately when it is added.
  • The indexed copy remains unchanged until the user explicitly refreshes it, re-adds the link, or uses a Refresh sources action.
  • Retrieval results should retain the original URL and the time at which the page was fetched.
  • Automatic periodic URL refresh is not part of the initial design.

5. Feasibility assessment

The application is feasible on a CPU-only Windows machine with 16 GB RAM if it uses small specialized models and aggressively prioritizes work.

The system should not run a generative model against every partial transcript. Audio capture and transcription must remain continuous, while proactive generations are selective, bounded, cancellable, and limited to short outputs.

Latency depends heavily on the exact CPU. Reasonable design targets, to be validated on representative hardware, are:

  • Partial transcript updates approximately 1–4 seconds behind speech.
  • Retrieval results approximately 1–3 seconds after a topic or question trigger.
  • Short generated suggestions commonly within approximately 4–15 seconds.

These are engineering targets rather than guarantees. The application should benchmark the device during setup and expose a low-latency model profile when a larger model cannot keep pace.

Meaning of local

Strictly offline operation can include audio capture, transcription, file ingestion, embeddings, retrieval, and generation, but it cannot fetch new web content. Fetching a supplied URL or performing live web search necessarily uses the network.

The intended privacy boundary is therefore:

  • Meeting audio and transcripts stay on the computer.
  • Local document content and embeddings stay on the computer.
  • Model inference stays on the computer.
  • Only URLs explicitly supplied by the user are fetched in the initial version.
  • Any future search feature should send a distilled search query, not the meeting transcript or private source material, and should be explicitly enabled.

6. Recommended technical approach

Use a native C# application with isolated native inference workers.

Application layer

  • Language/runtime: C# and .NET 10.
  • Desktop framework: WinUI 3 with Windows App SDK 2.4.
  • Windows integration: CsWin32 or focused P/Invoke wrappers for audio, hotkeys, window behavior, and process control.
  • Packaging: MSIX, with model assets downloaded or installed separately.

WinUI 3 is Microsoft's recommended framework for new native Windows desktop applications. A native application is preferred over an Electron-style shell because the target machine has limited RAM and must run multiple inference workloads alongside a conferencing application.

Inference isolation

Speech recognition and language generation should run in separate local worker processes rather than inside the UI process. The workers communicate with the application through named pipes using versioned JSON messages.

This provides:

  • UI responsiveness when inference is busy.
  • Cancellation and restart boundaries.
  • Crash isolation.
  • Independent model and runtime upgrades.
  • Straightforward performance measurement.

Alternatives considered

  1. Rust with Tauri: smaller distribution and attractive for future cross-platform work, but Windows audio, overlay, accessibility, and packaging integration would require more effort.
  2. Python with Qt: fastest for a disposable prototype and rich in ML libraries, but harder to package and control reliably as a polished Windows product.

The C# and native-worker architecture is the recommended product direction. Python remains useful for offline model evaluation and experiments, not as the main shipped application runtime.

7. Recommended model stack

Speech recognition

Initial choice: whisper.cpp with Whisper base.en.

Reasons:

  • Mature C/C++ implementation with Windows and CPU support.
  • Streaming example and controllable inference parameters.
  • Approximately 388 MB reported working memory for base.
  • OpenVINO acceleration is available on compatible Intel hardware.
  • The model can be upgraded to small.en when accuracy warrants the additional CPU and memory cost.

Evaluation candidate: Qwen3-ASR 0.6B Q8.

Qwen3-ASR is a newer streaming and multilingual option. It should be benchmarked against whisper.cpp on representative Windows x86 CPUs before adoption because readily published CPU figures are not sufficient to establish Windows performance.

Language generation

Initial choice: Gemma 4 E2B Instruct in Q4 GGUF format, served by llama.cpp.

Reasons:

  • Designed for edge and mobile deployment.
  • Official quantized GGUF checkpoints are available.
  • Its size leaves room for the conferencing client, speech recognition, retrieval, and Windows within 16 GB RAM.
  • It is suitable for short grounded responses, summaries, route selection, and citation-aware formatting.

Higher-quality option: Gemma 4 E4B Q4, enabled only when an installation-time benchmark shows acceptable generation speed and memory headroom.

Alternative: Qwen3.5 2B, subject to comparative testing for instruction following, grounded response quality, generation speed, and stable GGUF support.

Models in the 7B–12B range may fit when heavily quantized, but they are not recommended for this baseline. Fitting into memory does not mean they can generate quickly while the meeting application and ASR are active.

Embeddings

Choice: EmbeddingGemma 300M in Q8 or Q4 form.

Reasons:

  • Designed for on-device retrieval.
  • Supports multilingual text.
  • Provides flexible embedding dimensions.
  • Requires under approximately 200 MB RAM when suitably quantized, according to its documentation.

Voice activity detection

Choice: Silero VAD through ONNX Runtime.

VAD reduces unnecessary ASR work and provides useful speech-boundary events. It must remain a replaceable component so it can be tuned or substituted based on meeting-audio tests.

Audio capture

Use Windows Audio Session API loopback capture for system audio and a normal capture endpoint for the microphone. Keeping these channels separate provides a useful distinction between the local user and remote participants without running expensive speaker diarization.

The first version does not need to distinguish individual remote participants reliably.

Transcript stabilization

Streaming ASR emits partial and revised text. A transcript stabilizer should:

  • Track partial and final segments.
  • Prevent repeated words and overlapping windows from entering the canonical transcript.
  • Preserve timestamps and audio-channel identity.
  • Emit stable sentence or utterance events for downstream processing.
  • Allow corrections without repeatedly triggering the same suggestion.

Conversation state

Maintain two related forms of state:

  • A short verbatim window containing the most recent stable utterances.
  • A compact rolling summary of topics, entities, questions, claims, decisions, and unresolved items.

The rolling summary must have a strict token budget. It should be updated less frequently than the transcript and should not require an expensive generation for every utterance.

Proactive trigger engine

The trigger engine decides whether new conversation material merits retrieval or generation. It should combine inexpensive signals:

  • Direct or implied questions.
  • Topic and named-entity changes.
  • Claims that may benefit from evidence.
  • Numbers, dates, product names, people, or organizations found in indexed sources.
  • Decisions, objections, risks, and unresolved action items.
  • Semantic similarity between the current conversation and indexed content.
  • Cooldowns, deduplication, and novelty thresholds.

Retrieval can happen more often than generation. An LLM call should occur only when there is sufficient evidence that a suggestion will be useful.

Hybrid retrieval

Use both lexical and vector retrieval:

  • SQLite FTS5 handles exact names, acronyms, identifiers, and quoted phrases.
  • EmbeddingGemma with sqlite-vec handles semantic similarity.
  • A small fusion layer combines and deduplicates results.
  • The evidence selector favors fresh, directly relevant, and diverse passages.
  • Generated suggestions must retain references to the underlying chunks and sources.

A dedicated neural reranker is deferred. It adds memory and CPU pressure and should be introduced only if measured retrieval quality requires it.

9. Source ingestion

Local directories

The initial supported formats should be PDF, DOCX, Markdown, plain text, and HTML.

Proposed libraries:

  • PdfPig for PDF text extraction.
  • Open XML SDK for DOCX.
  • AngleSharp for HTML parsing.
  • Native text and Markdown parsing for simple formats.

Ingestion flow:

  1. Monitor configured folders with FileSystemWatcher.
  2. Debounce duplicate and partial-write events.
  3. Extract text and structural metadata.
  4. Split content using headings, paragraphs, lists, and page boundaries where available.
  5. Store source metadata and a content hash.
  6. Generate embeddings for changed chunks only.
  7. Update the lexical and vector indexes transactionally.

Web links

URL ingestion flow:

  1. Validate the URL and apply network-safety rules.
  2. Fetch immediately with an HTTP client.
  3. Enforce redirect, response-size, timeout, MIME-type, and scheme limits.
  4. Extract the page's primary readable content.
  5. Record the canonical URL, title, fetched timestamp, content hash, and retrieval status.
  6. Chunk and index the extracted text locally.
  7. Fall back to Playwright using installed Microsoft Edge only when ordinary HTTP extraction cannot obtain useful content from a JavaScript-rendered page.

The indexed page is a snapshot. It is refreshed only through explicit user action. Authentication-protected sources, robots and site terms, paywalls, and pages that prohibit automated access require careful handling and are not assumed to work in the first version.

10. Scheduling and resource control

CPU scheduling is a core product requirement, not a later optimization. Each subsystem should submit cancellable work to bounded queues.

Priority order:

  1. Audio capture, which must never wait on model work.
  2. VAD and ASR.
  3. User-requested retrieval.
  4. User-requested generation.
  5. Proactive retrieval.
  6. Proactive generation.
  7. File indexing and URL refresh.

Only one language-model generation should run at a time on the baseline machine. A newer high-priority request should cancel an obsolete proactive generation. Background indexing should pause or throttle during active calls.

Suggested response length should normally be constrained to approximately 40–100 tokens. The UI can request a longer continuation when the user explicitly chooses a route requiring more detail.

12. Reliability, privacy, and safety

  • Show an unambiguous listening indicator and explicit session start/stop controls.
  • Make transcript persistence opt-in; support an ephemeral session mode.
  • Do not include raw transcripts in routine logs.
  • Store local indexes in a user-controlled application-data location.
  • Support deleting a source and all derived chunks and embeddings.
  • Label suggestions as generated assistance and keep citations visible.
  • Do not present uncertain generated content as verified fact.
  • Track transcript confidence and avoid strong suggestions from unstable text.
  • Treat downloaded content and documents as untrusted input; source text must never override application-level instructions.
  • Protect URL fetching against local-network access, unsupported schemes, excessive redirects, very large downloads, and decompression bombs.
  • Respect organizational policy, participant expectations, and applicable consent requirements for meeting capture and transcription.

13. Testing and evaluation

Model evaluation

Create a representative, locally controlled meeting-audio corpus containing clean speech, accents, cross-talk, conferencing compression, background noise, names, acronyms, and domain terminology.

Compare candidate ASR models on:

  • Word error rate and domain-term accuracy.
  • Stable partial-transcript latency.
  • Real-time factor on baseline CPUs.
  • Peak RAM and sustained CPU usage.

Compare candidate LLMs on:

  • Groundedness in retrieved passages.
  • Citation correctness.
  • Short-answer usefulness.
  • Instruction following.
  • Time to first token and tokens per second.
  • Peak RAM while ASR remains active.

Component tests

  • Audio buffer overflow and device changes.
  • Partial transcript revision and deduplication.
  • Trigger cooldowns and stale-work cancellation.
  • Chunking and source-location preservation.
  • Hybrid retrieval ranking.
  • URL validation, timeouts, content limits, and refresh behavior.
  • File changes, deletions, renames, and interrupted writes.
  • Worker crash and restart recovery.

End-to-end acceptance tests

  • The transcript remains responsive throughout a representative call.
  • Adding a local folder makes its supported documents searchable.
  • Adding a URL fetches and indexes it immediately.
  • The URL is not refreshed until explicitly requested.
  • A relevant conversational topic produces a grounded suggestion without a direct question.
  • A stale generation is cancelled when the conversation moves to a new topic.
  • Every source-grounded suggestion can navigate back to its file location or URL.
  • The app remains within the measured CPU and memory envelope on a 16 GB reference machine.

14. Proposed MVP sequence

Phase 1: feasibility harness

  • Capture WASAPI loopback and microphone audio.
  • Run streaming whisper.cpp transcription.
  • Measure latency, CPU, memory, and transcript stability on several Windows CPUs.
  • Benchmark Gemma 4 E2B and E4B while ASR is active.

This phase determines whether the default model profile meets the product's responsiveness target.

Phase 2: local retrieval foundation

  • Add the SQLite schema, FTS5, and sqlite-vec.
  • Ingest supported local files.
  • Add immediate URL ingestion and explicit refresh.
  • Preserve citations and freshness metadata.

Phase 3: conversation intelligence

  • Stabilize streaming transcript segments.
  • Maintain bounded conversation state.
  • Implement proactive triggers, novelty controls, and retrieval fusion.
  • Generate short grounded suggestions with citations.

Phase 4: desktop teleprompter

  • Add the always-available Windows widget or overlay.
  • Display live status, transcript health, and suggestion cards.
  • Add user-selectable routes, cancellation, and session controls.
  • Package the application and model installation flow.

15. Decisions intentionally deferred

  • Exact overlay layout and card expansion behavior.
  • Whether session transcripts persist by default or only when explicitly saved.
  • The first supported CPU generation and minimum acceptable benchmark score.
  • Whether multilingual transcription is required for the initial release.
  • Which web-search provider, if any, should be added beyond user-supplied URLs.
  • Authentication support for protected web pages or enterprise repositories.
  • Whether future versions target macOS or Linux.

Addendum: Edge intelligence runtime research

Research date: 29 August 2026
Scope: Kompact AI and comparable local inference options for the Windows x64, CPU-only, 16 GB MVP.

Conclusion

Kompact AI should be evaluated, but should not be a hard dependency of the MVP. It is Ziroh Labs' proprietary CPU-first inference platform, not the similarly named open-source context-compression proxy. Ziroh presents it as a runtime for text, speech, vision, multimodal models, RAG, and on-device copilots, with OpenAI-compatible clients and local deployment.

The concept fits this product, but the public evidence is not yet sufficient for a redistributable consumer Windows application. Public material does not establish a Windows desktop support matrix, a 16 GB laptop memory profile, self-service runtime availability, a stable SDK contract, desktop redistribution terms, or incremental streaming-ASR behavior. Its download route currently leads to vendor contact rather than a public runtime package. These gaps should be treated as evaluation risks, not as evidence that the product cannot work.

Architecture adjustment

The research reinforces the decision to avoid a single all-encompassing “AI platform” abstraction. The product should expose four narrow capabilities:

ITranscriber
  AcceptAudio(frame) -> partial/final transcript events

IEmbedder
  Embed(query/documents) -> versioned vectors

IRetriever
  Search(query, filters) -> cited evidence

IGenerator
  Stream(request, cancellation) -> suggestion tokens and metadata

The internal contracts should include deadlines, priorities, cancellation reasons, source identifiers, timing, runtime/model versions, and privacy state. Provider-specific OpenAI-compatible APIs remain adapters rather than becoming the application's domain interface.

Updated recommendation

  • Keep the production baseline: C#/.NET orchestration, isolated workers, whisper.cpp, ONNX Runtime, SQLite FTS5 plus wrapped sqlite-vec, and llama.cpp.
  • Benchmark sherpa-onnx against whisper.cpp using representative meeting recordings, measuring partial latency, finalization latency, word error rate, CPU use, and RAM.
  • Create a Foundry Local generation spike after the first vertical slice, without coupling the product to its current API.
  • Use OpenVINO only when hardware detection and benchmarks show a meaningful benefit on Intel devices.
  • Ask Ziroh for a Kompact AI Windows trial, documentation, redistribution terms, telemetry details, and named-hardware benchmarks.
  • Adopt Kompact for an individual capability only if it wins the end-to-end benchmark and satisfies offline, privacy, licensing, packaging, and cancellation requirements.

Kompact AI evaluation gate

Before building an adapter, obtain written answers covering Windows versions and CPU requirements; offline installation and activation; telemetry and network destinations; API versioning and cancellation; runtime and model redistribution; signed binaries and security response; streaming ASR semantics; embedding versioning; and memory use for simultaneous ASR, embeddings, and a small LLM.

Benchmark it on the target computer while Meet, Zoom, or Teams is active. Measure end-to-end time from conversational cue to cited card, time to first token, tokens per second, cancellation latency, peak working set, CPU utilization, transcription delay, call quality, UI responsiveness, and thermal throttling.
